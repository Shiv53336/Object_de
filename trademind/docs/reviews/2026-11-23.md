# Review, 2026-11-23

A full review of the repo was run in Claude Code on the owner's laptop and returned 74 findings. This file lists the main themes, what changed in response, and what is still open. Where an item maps to a decision or a task card, the reference is given.

## 1. Statistics and the promotion gate (fixed, D29)

The gate could be made to pass by looking at the same data again and again.

| Finding | Change |
|---|---|
| The holdout was "everything after the research end", so it kept growing and could be re-read. | A fixed window, 2026-05-01..2026-10-31 (`validation.holdout_end`). |
| Holdout looks were counted per strategy version. A new version reset the count. | 2 looks per strategy per window, across all versions, timeframes and parameters. |
| Trials and looks were counted in the local database. A new machine or a fresh DB reset them. | A git-tracked ledger (`ledger/hypotheses.jsonl`, `ledger/holdout_looks.jsonl`). `validate` refuses to run with uncommitted ledger changes. |
| Bonferroni counted the trials in one run, not every hypothesis ever tested. | Bonferroni counts distinct real-data hypotheses across all strategies. Synthetic runs do not count and cannot be validated. |
| The bootstrap resampled single trades, which are correlated within a day. | The bootstrap resamples whole trading days. |
| A run with missing sessions could still be validated. | Runs need 90% session coverage (`validation.min_session_coverage`). Runs store `n_sessions`, `first_session` and `last_session`. |
| `validate` read the holdout before checking the research run existed. | It checks the matching research run (version, parameters, config hash) first, and refuses before reading holdout data. |
| The scoreboard did not show what costs take. | New `gross_expectancy_r` and `cost_per_trade_r` columns; `--by year` and `--by quarter`. |

## 2. Database migrations (fixed, T06)

Schema changes needed a manual rebuild. Alembic now runs on startup:
- **New databases** are created at the head revision.
- **Older databases** are stamped at `0001` and upgraded.
- **Manual upgrade:** `trademind db upgrade`.

## 3. Live paper reliability (fixed, D30)

| Finding | Change |
|---|---|
| A stalled tick stream produced empty minutes that the engine treated as real. | After 30 s with no ticks, the engine stops processing. It fills the gap from Kite minute candles every 20 s, alerts after 10 minutes with no data at all, and records stalls, filled and empty minutes in the run's notes. |
| A crash or Ctrl+C left a run looking finished. | Runs end as `done`, `stopped`, `crashed` or `superseded`. Only `done` days count as paper days. |
| A restart on the same day started a second run beside the first. | The new run resumes the aggregator and marks the old run `superseded`. |
| A live paper run could start on a holdout day. | Refused. |
| Paper fills used fixed slippage with nothing to check it against. | Best bid/ask is captured into a `quotes` table. `paper check` section 4 reports execution drift per trade. |
| Alerts were missing for failures. | Telegram alerts for a crash, a stall that gives up, and backup or restore-test failure (`deploy/notify.sh`). |

## 4. Data integrity (fixed, D30)

| Finding | Change |
|---|---|
| Live bars and synthetic bars shared the research store. | Three stores: `data/bars` (exchange candles only), `data/bars_live`, `data/bars_synthetic`. |
| A crash mid-write could leave a half-written parquet file. | Writes go to a temp file and are then renamed. |
| Splits and bonuses showed up as huge overnight moves. | `data validate` flags overnight jumps over 20%. Bars are adjusted on read from `config/corporate_actions.yaml`. |
| The stock list is today's large caps. | Not fixable with the current data. Noted in `CHARTER.md`, with the fix planned in T21. |

## 5. Windows laptop path (fixed)

`Step` in the PowerShell scripts returned the command's output instead of its exit code, so failures looked like success. Fixed in `deploy/windows/common.ps1`, with a Windows-only test. `daily.ps1` and `daily.sh` now download recent candles, run preflight and run `paper check`.

## 6. Ops agent and security (fixed, D31)

| Finding | Change |
|---|---|
| The workflow gave the self-hosted runner, where Claude runs, a token that could push. | Three jobs. **task** (self-hosted, read-only token) returns a git bundle. **verify** (GitHub-hosted) runs ruff and pytest on it. **publish** (GitHub-hosted) runs only main's `publish.sh`, which accepts only `agent/*` branches, requires the bundle to build on main, and scans the diff for credentials before pushing and opening a PR. |
| The Bedrock cap was enforced in code only, and failed open if its ledger was damaged. | The cap fails closed. The fallback is off by default: at 0, the role has no Bedrock access at all. Above 0, an AWS Budgets action attaches a deny policy at 100%. |
| The AWS budget ($60) only sent an email, and was sized for a $20 agent fallback. | $45 (`monthly_budget_usd`), with the fallback off; the Budgets action above is the hard stop when it is on. |
| `setup.sh` would register a runner on a public repo. | It refuses while the repo is publicly visible. |
| Backups could fail silently and were never restored to check them. | Backups alert on failure, check the dump size, and sync the ledger. A weekly restore test (Sundays 10:00 IST) restores into a scratch database and compares row counts. |

**Residual risk.** Claude fully controls the `agent` user on the self-hosted machine. It does not have:
- `.env` (OS permissions)
- `sudo` beyond the fixed scripts
- a write token
- AWS rights beyond Bedrock

Keep the repo private, and keep secrets off that user. See `AGENT.md`.
